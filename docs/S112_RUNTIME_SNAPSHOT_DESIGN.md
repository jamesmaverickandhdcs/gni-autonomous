# S112 - THE DATABASE SNAPSHOT A RUNTIME FITNESS FUNCTION MAY READ (DESIGN, NOT BUILT)

Written at S112, before any fitness function reads it: roadmap 4's OWED list
(`GNI_ARCHITECTURE_S111.md`, "a snapshot a runtime fitness function may read", needed by R4-3) and
the S112 mission, clause (b), both ask for this design in writing first. Nothing here is built. A
later session builds it only after James rules on section 8.

## 1. THE PROBLEM, IN ONE PARAGRAPH

Five claims on the public pages carry a number that only the database knows (section 3). The
detector is deterministic and offline: a fitness function that queried Supabase would put a
network call and a secret inside `tools/gni_rule_checks.py`, which S104 refused for the secret
list. Section six of ARCHITECTURE already solved the same problem for the GitHub run history: a
separate, explicit harvest writes a git-tracked snapshot, and the generator reads only the
snapshot (`tools/gni_runtime.py`, DECISION S99-1). This design applies that precedent to the
database, and the S112 external snapshot (`docs/gni_external_snapshot_S112.json`, F-EXT) supplies
the shape of a fact.

## 2. THE GUIDELINES IT FOLLOWS

- **W3C PROV-DM** (the PROV data model). Every figure in the snapshot is an *entity* generated by
  an *activity* (one named read-only query, run once) that *used* the database and is *attributed
  to* an *agent* (the operator who ran it). The snapshot records all four, so a reader can ask of
  any number "made by what, from what, by whom, when" and get an answer from bytes.
- **ISO/IEC 25012:2008** (data quality model), two characteristics named on purpose:
  *traceability* - the figure's lineage is auditable (the query text is stored beside its result,
  and the query file is in the tree with an md5); *currentness* - the figure is up to date for the
  use it is put to (section 5 says what "up to date" means here, and derives it rather than
  typing a number of days, so C5 has nothing to object to).

## 4. THE SNAPSHOT

`docs/gni_db_snapshot_S<N>.json`, session-numbered like every close artifact; the live one is the
highest number. One file, written whole by the operator, never edited by hand afterwards.

```json
{
  "about": "...",
  "query_file": "tools/gni_db_harvest.sql",
  "query_md5": "<EOL-normalised md5 of the query file at harvest>",
  "harvested_at": "<the database's now(), not a laptop clock>",
  "harvested_by": "the operator, S<N>",
  "facts": [
    {"id": "groq-tokens-main-2026-08", "kind": "dated",   "window": "2026-08-01/2026-09-01",
     "rows": 61, "value": {"mean": 17780, "n": 61}},
    {"id": "public-tables",            "kind": "current", "window": "at harvest",
     "rows": 1,  "value": {"count": 33}}
  ]
}
```

- **One query, one JSON cell.** `tools/gni_db_harvest.sql` is a single read-only `select
  json_build_object(...)`. Its result is ONE row and ONE cell, which the operator copies into the
  file. One row cannot meet the SQL Editor's 100-row grid limit (R-S111-3), and every fact still
  carries the row count of the set it was computed from.
- **The query is in the tree, and its md5 is in the snapshot.** A snapshot whose `query_md5` does
  not match the query file at its own commit is refused: a figure is traceable only to the query
  that actually produced it.
- **The fact ids are named by the query, not by the claims.** A claim binds to a fact; a fact
  does not know which claims read it, so one fact can support a sentence on two pages (CLM-231).

## 5. THE FITNESS FUNCTION, AND WHAT "CURRENT" MEANS

`F-DB` (one function, like F-EXT): a binding names a fact id and a verbatim fragment of the
claim; the fragment's number must equal the fact's value **as the page rounds it** - the rounding
is read from the fragment itself (`~17,780` is an integer; `7.4K` is one decimal of thousands),
never typed into the function.

- **dated** facts (`window` is a closed interval in the past) never go stale: August 2026 does
  not change. The claim must name the same window ("Aug 2026"), or the binding is refused.
- **current** facts (`window` = "at harvest") are current only while the snapshot is the one the
  claims generation was written against: the check reads the highest-numbered DB snapshot and
  the highest-numbered claims document, and a current fact is accepted only when the two session
  numbers are equal. Both numbers come from file names, so no age in days is hand-written (C5).
  The cost is said plainly: every session that writes a claims document must harvest the
  database again, or its current-state claims fall back to UNMEASURED (RUNTIME) - visibly, in the
  count, not silently.

Proof that it can fail: a fact whose value differs from the page (RED on C13); a snapshot whose
`query_md5` does not match its query file (INSTRUMENT ERROR); a current fact read against a
claims document of a later session (the claim drops to UNMEASURED and NUMBERS UNDERIVED rises,
RED on C18); a dated fact whose window the claim does not name (refused). As built (section 9)
these are failure tests run on a copy before the commit, as for F-EXT, not fixture families: the
fixture exercises C13 through one generic binding (F-ROUTES) and holds no fitness function's own
case.

## 6. WHAT IT CANNOT DO (WRITTEN DOWN, NOT DISCOVERED LATER)

- It cannot prove the operator pasted the cell unaltered. The query md5 proves which query was
  meant; nothing proves the result. Trust is the operator's, as F-EXT's `$0.00` attestation is.
- It cannot see a figure between harvests. A current fact is true at `harvested_at` and claimed
  for the rest of that session only.
- It measures what the database holds, not what happened: tokens a run spent but did not log are
  invisible (the S110 note on `groq_daily_usage` coverage applies).

## 7. WHAT IT REPLACES AND WHAT IT DOES NOT

Section six's snapshot stays as it is (GitHub run history, `tools/gni_runtime.py`); this one is
the database's. They are two sources and stay two files: one finding, one home (CONTRACT
ROUTING). F-EXT stays for parties GNI does not control; F-DB is for GNI's own data.

## 8. FOR JAMES TO RULE BEFORE IT IS BUILT

A - build it as designed (one query file, one snapshot per claims generation, F-DB, four fixture
families). B - build it for the two DATED facts only and relabel the two CURRENT-state sentences
count-free, so no session is ever obliged to harvest. C - do not build it; make all five
count-free. Claude's lean at S112: **B** - the dated figures are the ones a reader uses to judge
cost, and the current ones ("33 tables", "since 2026-06-23") would make every future session pay a
harvest to keep two sentences green.

## 9. AS BUILT AT S112 (DECISION S112-4 = B, delegated by the operator) - WHAT DIFFERS FROM ABOVE

- **Scope B.** Two DATED facts only (August 2026 Groq tokens for `gni_pipeline` and `gni_mad`).
  CLM-321's date and CLM-835's table count were made count-free; no CURRENT fact exists, so the
  session-equality rule of section 5 is designed and not built.
- **Two fitness ids, not one.** `F-DB-PIPE-TOKENS` and `F-DB-MAD-TOKENS`: a fragment such as
  `~17,717/run (mean of 63 logged runs, Aug 2026)` does not name its pipeline, so the binding's
  fitness id does. Both read the same snapshot through one loader that checks `query_md5`.
- **The snapshot wraps the operator's cell.** The cell (`harvested_at`, `facts`,
  `pipelines_in_window`) is copied unaltered under `harvest`; `about`, `query_file`, `query_md5`
  and `harvested_by` were added around it by Claude. Section 4 said the operator writes the file
  whole; the cell is the operator's, the wrapper is not.
- **The harvest falsified the published figures (the reason this was worth building).** The pages
  said `~17,780/run (61 runs)` and `~68,509/run (61 runs; range 7.4K-97K)` for August 2026, as
  S90 measured them on 2026-08-31. The whole month reads 63 and 62 logged runs, means 17,717 and
  68,525, and a MAD range of 61.9K-74.2K. The means moved because S90 read the month before it
  ended. The range is not reproducible from August at all - 7.4K and 97K lie far outside every
  August value - so the published range came from some other window, which the record does not
  name. The pages now carry the figures the snapshot derives.
- **R9: two more DATED facts, and a "first row" is dated when its window is closed.** CLM-894 said
  "Report-level GPVS verification has been live since April 2026". `gpvs-report-outcomes-first`
  and `reports-first` take the first `created_at` of `prediction_outcomes` and of `reports` in a
  window ending 2026-10-01: a closed past window, so its first row cannot change unless rows are
  deleted, and no code deletes either table's rows. A `columns` entry reports whether
  `prediction_outcomes.created_at` exists, because the fact is read through `to_jsonb` so the
  query cannot fail; `run_at` (the report's own date) is never used in its place. The first R9
  harvest (window ending 2026-05-01) read ZERO verification rows; the second read the first
  verification on 2026-05-27 and the first report on 2026-05-24. The database is therefore no
  older than late May, so it can neither confirm nor refute an April start in an earlier store;
  the page now says what the record shows ("on record since May 2026, when the database's first
  reports were stored"), and F-DB-GPVS-SINCE holds both months to that sentence. Both harvests
  reproduced the two August facts byte for byte - the dated design's own check.
